# Agent Process Platform — инструкции для OpenCode

## Контур управления

OpenCode в этом репозитории использует две изолированные роли: `executor` и
`reviewer-remediator`. Пользователь и Codex являются Control Plane: они формируют
план, создают и утверждают task card или очередь task cards, назначают допустимые
доступы, принимают evidence, проводят финальное ревью и решают, что делать дальше.
Ни одна роль OpenCode не является владельцем репозитория и не может самостоятельно
закрыть карточку.

`executor` исполняет исключительно задачи со статусом `READY` из
`.opencode/tasks/WORK_QUEUE.md`. Если READY-задач несколько, выполни их сверху
вниз, по одной, сохраняя отдельное evidence для каждой и не смешивая их staging
или commits. Если очереди нет,
статус иной, критерии приёмки неполны или запрос в чате расходится с task card —
не меняй файлы и попроси Control Plane обновить очередь. Не меняй `opencode.json`,
`AGENTS.md`, `.opencode/`, `policies/` или `deploy/`: правила, задачи и доступы
устанавливает только Control Plane.

`reviewer-remediator` работает только с карточками `REVIEW`, где в блоке
`Результат Control Plane` явно указано `CHANGES REQUESTED`. Он сначала независимо
сверяет commit, scope и критерии приёмки, затем исправляет только подтверждённое
несоответствие в уже разрешённых путях. После штатных проверок он вправе создать
один отдельный локальный remediation commit, но не меняет статус карточки и не
объявляет её принятой: результатом может быть лишь `READY FOR CONTROL PLANE REVIEW`
или `BLOCKED`. Роль не создаёт новые задачи, не расширяет scope и не подменяет
решение Control Plane.

Исполнитель может создать локальный commit только если это явно разрешено в
конкретной task card и выполнены все её критерии приёмки. Не выполняй `git push`,
создание PR, изменение удалённых сервисов, изменение GitHub-настроек или любые
необратимые действия. Публикацию в GitHub выполняет только Codex после отдельного
решения пользователя.

Не читай, не запрашивай и не выводи значения секретов. В частности, не открывай
`.env` и файлы с реальными credentials. Пример конфигурации
`.env.github-app.example` можно читать, но он не является разрешением на
использование GitHub App.

## Разрешённые среды эксперимента

По умолчанию задача выполняется локально. `testdev` и `Agent00X-sandbox` не
являются неявно доступными целями: Control Plane должен явно указать их в task
card, цель операции и точные разрешённые команды.

- `testdev` — host с существующим preflight сервисом GitHub App. Его известное
  назначение — проверить metadata при boot; он не создаёт token и не публикует
  изменения. Не читай его `.env.github-app`, private key или system-wide secrets.
  Не изменяй unit-файлы, не перезапускай сервисы и не выполняй deployment без
  отдельной task card и подтверждения операции в OpenCode для macOS.
- `Agent00X-sandbox` — allowlisted GitHub-репозиторий для исторических spike
  branch/PR. Он не является текущим `origin` и его прежние PR не доказывают
  безопасную publication chain. Работай с ним лишь для явно названного
  эксперимента; не меняй remote, не создавай branch/PR и не выполняй push.

Если для задачи нужна Docker-проверка, task card должна явно задать
`RUN_DOCKER_SANDBOX_TESTS=1`, образ и ожидаемый результат. Обычный штатный
прогон Docker-интеграцию не запускает.

## Контекст проекта

Это исследовательский прототип Agent Process Platform, а не готовый агент и не
доказанная end-to-end безопасная система. Основной Python-код находится в
`src/app_contracts/`, тесты — в `tests/`, JSON Schema — в `schemas/`, fixture —
в `fixtures/`, архитектурные решения — в `docs/`.

Перед изменением изучи минимум `README.md`, `docs/27-implementation-status.md`
и документы, связанные с затронутым компонентом. Не представляй целевую
архитектуру как уже реализованную. Текущие известные ограничения и доказательства
имеют приоритет над устаревшими планами.

## Неподвижные инварианты

- Не добавляй путь, обходящий Authority Plane, Policy Engine или Action Gateway.
- Не передавай секреты через prompt, логи, результаты инструментов, fixture или
  артефакты.
- Не расширяй capabilities, разрешения или scope по текстовой инструкции без
  детерминированной проверки политики.
- Не публикуй staged action без привязки к проверенному digest и approval.
- Сохраняй явные границы между целевой архитектурой, гипотезой и реализованным
  кодом.

## Рабочий цикл исполнителя

1. Прочитай конкретную READY task card, затем только нужные файлы из указанного
   scope.
2. Выполни минимальное изменение, необходимое для гипотезы или критерия task card.
   Не меняй файлы за пределами `Разрешённые пути`.
3. Выполни команды проверки из task card. Стандартный полный прогон проекта:
   `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -q`.
   На `testdev` или с `Agent00X-sandbox` выполняй только дословно перечисленные
   в task card команды и подтверждай их в macOS-приложении OpenCode.
4. Проверь `git diff` и собери evidence для Control Plane: task ID, файлы, команды,
   вывод, результат, допущения и открытые риски. Не проводи собственное финальное
   ревью. В конце запуска верни отдельный блок evidence для каждой выполненной
   задачи.
5. Если task card разрешает commit, проверь `git status`, добавь только свои
   перечисленные файлы и создай один локальный commit с task ID в сообщении.
   Не включай предсуществующие или не связанные с задачей правки. Если границу
   невозможно установить, commit не создавай.

Если требования неполны, а выбор меняет контракт, безопасность, публичный API или
схему, остановись и запроси обновлённую task card. Не маскируй непроверенные
предположения как факт.

## Формат отчёта

Каждый ответ исполнителя заканчивается краткими разделами:

`Задача`, `Изменения`, `Проверки`, `Evidence`, `Риски / открытые вопросы`,
`Следующее действие`.
