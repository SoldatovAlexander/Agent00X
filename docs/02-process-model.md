# Модель процессов

Статус: принята концептуально; детали требуют валидации

## Процесс как основной объект

Процесс — версионированная машина состояний, которая связывает цель,
ответственность, входы, шаги, полномочия, доказательства и результат.

Workflow является авторитетным владельцем порядка, состояния, таймеров,
переходов и журнала. Агент получает снимок необходимого состояния, предлагает
результат или действие, но не становится единственным хранилищем процесса.

```yaml
process:
  id: process-42
  definition: repository-change/v1
  objective: "Обновить зависимость без изменения публичного API"
  owner: user-12
  participants: [orchestrator, worker, verifier]
  inputs: []
  acceptance_criteria: []
  data_classification: internal
  risk_class: medium
  budget:
    money: 5.00
    duration: 30m
    strong_model_calls: 2
  approval_policy: before-apply
  rollback_policy: compensating-action
```

## Состояния задачи

```text
proposed -> authorized -> running -> verifying -> staged -> approved -> applied
                  |          |          |           |
                  +------ failed / retry / escalated+
```

Переход содержит инициатора, timestamp, входной и выходной digest, policy
decision, evidence и correlation ID.

Жизненный цикл агентной или A2A-задачи не совпадает с состоянием бизнес-объекта.
Завершение удалённой задачи само по себе не переводит объект процесса дальше:
сначала workflow валидирует результат и разрешённый переход.

## Выбор уровня автоматизации

Для каждого шага сначала выбирается минимально достаточная форма:

1. Обычный детерминированный workflow.
2. Узкая AI-функция без инструментов и автономности.
3. Один специализированный агент с ограниченным контрактом.
4. Несколько агентов при наличии разных компетенций, прав, источников,
   независимой проверки или полезного параллелизма.

Количество агентов не является целью или показателем зрелости.

## Task Contract

Подзадачи передаются между агентами только как ограниченные контракты:

- objective;
- входные ссылки на данные и артефакты;
- разрешённая область изменений;
- ограничения;
- критерии приёмки;
- deliverables;
- capabilities;
- бюджет и deadline;
- политика эскалации.

Свободный текст допускается внутри полей контракта как данные, но не заменяет
его обязательные структурные поля.

## Evidence Bundle

Результат агента включает:

- созданные артефакты и их digest;
- тесты и машинно-проверяемые результаты;
- источники и provenance;
- список предположений;
- известные ограничения;
- несоответствия критериям приёмки;
- оценку неопределённости;
- затронутые ресурсы.

## Надёжность

- внешние действия используют idempotency key;
- шаги имеют timeout и ограниченные retry;
- необратимые действия требуют явной политики;
- долгие ожидания сохраняются как состояние, а не удерживают процесс;
- компенсация является отдельным авторизованным действием;
- approval связывается с digest и отзывается при изменении входов или политики.

## Конфликты процессов

Runtime должен обнаруживать пересечение ресурсов, поддерживать optimistic
concurrency и не применять устаревшие approvals. Политика разрешения конфликтов
остаётся открытым вопросом и будет проверена на сценариях разработки и внешних
операций.

## Связанный пакет процесса

Процесс считается подготовленным не при наличии набора документов, а когда
между ними прослеживаются связи:

- паспорт и границы процесса;
- роли, ответственность и владелец решения;
- сценарии, операции и исключения;
- состояния и разрешённые переходы;
- бизнес-правила и таблицы решений;
- сущности, данные и документы;
- источники знаний и их владельцы;
- карта контекста агента;
- карточки и контракты агентов;
- реестр инструментов и capabilities;
- тесты, риски, approvals и журналирование.

Каждый тест должен ссылаться хотя бы на сценарий, правило, состояние, контракт
или запрет. Каждый инструмент — на владельца, допустимые состояния, право,
ошибки, идемпотентность и аудит.
