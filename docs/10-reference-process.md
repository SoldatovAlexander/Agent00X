# Эталонный процесс PROC-001

Название: безопасное изменение программного проекта  
Статус: гипотеза для архитектурной валидации; это целевой процесс, а не
подтверждённый сквозной сценарий. Фактический статус — в документе 27.
Версия: 0.1  
Дата: 2026-09-03

## Паспорт процесса

| Поле | Значение |
|---|---|
| ID | `PROC-001` |
| Цель | Подготовить, проверить и применить ограниченное изменение проекта без раскрытия секретов и обхода полномочий |
| Владелец | Пользователь, инициировавший изменение |
| Начало | Получен запрос на изменение проекта |
| Завершение | Одобренный digest опубликован как PR либо процесс безопасно завершён без внешнего изменения |
| Основной объект | `ChangeRequest` |
| Результат | Patch, evidence bundle, verification report, Pull Request и action receipt |
| Риск | Средний по умолчанию; высокий при секретах, внешних системах или необратимых действиях |
| SLA прототипа | Не определяется до измерений |
| KPI валидации | Изоляция секретов, отсутствие обхода Gateway, корректное восстановление, качество и стоимость маршрутизации |

## Границы

### Входы

- пользовательская цель и критерии приёмки;
- ссылка на разрешённый snapshot репозитория;
- классификация проекта и данных;
- максимальный бюджет;
- допустимые внешние интеграции;
- политика approvals.

### Выходы

- подготовленный patch с digest;
- результаты тестов;
- перечень изменённых ресурсов;
- assumptions и unresolved risks;
- решение verifier;
- запись об approval или отказе;
- action receipt при применении.

### Вне процесса

- изменение production без отдельного класса процесса;
- выдача агенту постоянного credential;
- самостоятельное изменение политик агентом;
- публикация в удалённый репозиторий без явной capability;
- физическое управление устройствами через MHS — отдельный процесс валидации.

## TO-BE сценарий SC-001

Перед каждым пунктом, где агент принимает процессное решение, и перед каждым
вызовом инструмента Runtime сохраняет checkpoint и Observation Event. Отказ этой
записи запрещает новое действие; результат, ошибка или неизвестный исход
сохраняются отдельным связанным событием. Это требование целевого сценария,
пока не реализованное в `PROC-001`.

1. I/O Gateway принимает запрос пользователя и создаёт canonical envelope.
2. Workflow создаёт `ChangeRequest` в состоянии `received`.
3. Оркестратор уточняет контракт только при недостающих критичных данных и
   формирует `TaskContract`.
4. Policy engine вычисляет максимально допустимые capabilities процесса.
5. Model Router выбирает worker по сложности, риску, приватности и бюджету.
6. Sandbox Supervisor создаёт одноразовое рабочее пространство без секретов и
   прямого сетевого доступа.
7. Worker исследует snapshot и подготавливает patch и evidence bundle.
8. Test Runner выполняет разрешённые проверки вне произвольного контекста LLM.
9. Verifier независимо сопоставляет результат с критериями приёмки.
10. При недостатке доказательств workflow возвращает задачу, эскалирует модель
    или завершает процесс отказом согласно политике.
11. Если интеграционный тест требует credential, worker создаёт типизированный
    `SecretOperationRequest` без значения секрета.
12. Secret Guardian оценивает необходимость по метаданным, а policy engine
    принимает решение.
13. Credential Broker выполняет только именованную операцию и возвращает
    очищенный receipt.
14. Workflow формирует `StagedAction`, связывая его с digest patch, тестами,
    политикой и состоянием проекта.
15. Пользователь получает preview и подтверждает точный digest вне обычного
    текстового ответа агента.
16. Перед публикацией Action Gateway повторно проверяет policy, состояние,
    approval, digest, base commit и idempotency key.
17. GitHub Actuator запрашивает у Credential Broker короткоживущий GitHub App
    credential, создаёт branch, commit и Pull Request и не раскрывает credential
    агентному контуру.
18. Результат проверяется, сохраняется как Action Receipt и возвращается
    владельцу.

19. Observer по запросу формирует отчёт из разрешённой истории, отделяя
    фактические события от заявленных оснований решения и интерпретации.

## Альтернативные сценарии

### SC-002: Дешёвая модель не прошла проверку

Workflow сохраняет evidence первой попытки и передаёт задачу более сильной
модели. Новая модель получает контракт и релевантные артефакты, но не скрытые
рассуждения первого worker.

### SC-003: Требуется уточнение пользователя

Процесс переходит в `waiting_input`, сохраняет deadline и освобождает worker.
После ответа проверяется актуальность snapshot, политики и бюджета.

### SC-004: Обнаружена prompt injection

Payload получает taint. Write-capabilities замораживаются. При высоком риске
материал помещается в quarantine и передаётся Security Investigator без
дополнительных прав.

### SC-005: Секретная операция запрещена

Credential Broker не вызывается. Worker получает машинную причину отказа без
сведений о credential. Workflow выбирает безопасную альтернативу или завершает
процесс.

### SC-006: Approval устарел

При изменении patch, snapshot, политики или значимого состояния прежний approval
аннулируется. Создаётся новый staged digest.

### SC-007: Сбой во время применения

Workflow сверяет idempotency key и receipt с внешней системой. Повтор допустим
только если действие доказуемо не было завершено либо является идемпотентным.

### SC-008: Разбор ошибки и учебная ветка

Владелец выбирает checkpoint до ошибочного решения, создаёт LearningCorrection
и запускает новую ветку в симуляции. Исходная история не меняется; прежние grants,
approval и внешние сессии не переносятся. Корректировка оценивается на новых
похожих задачах и регрессионном наборе до отдельного разрешения на применение.

## Исключения EX-001…EX-008

| ID | Условие | Реакция |
|---|---|---|
| EX-001 | Snapshot изменился | Пересобрать контракт и повторить verification |
| EX-002 | Превышен бюджет | Остановить или запросить расширение у владельца |
| EX-003 | Worker запрашивает лишнюю capability | Отказать и записать security event |
| EX-004 | Тесты неоднозначны или нестабильны | Отдельная диагностика, запрет apply |
| EX-005 | Verifier и worker расходятся | Эскалация арбитру или пользователю |
| EX-006 | Gateway или policy service недоступен | Read-only degraded mode, write запрещён |
| EX-007 | Обнаружена утечка в output | Заблокировать отправку и отозвать временные права |
| EX-008 | Невозможно определить результат внешнего действия | Состояние `reconciliation_required`, без слепого повтора |

## Критерии завершения

Процесс считается успешно завершённым, если опубликован именно одобренный digest,
критерии приёмки подтверждены evidence, секреты не раскрыты, side effects
связаны с receipts, а журнал позволяет восстановить ход выполнения.
