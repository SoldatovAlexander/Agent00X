# Бриф проекта Agent Process Platform

Статус: продуктово-архитектурный бриф 0.1  
Дата: 2026-09-04  
Назначение: единое описание продукта для команды, партнёров, экспертов и
потенциальных инвесторов

## 1. Краткое резюме

Agent Process Platform — локально-развёртываемая и расширяемая платформа для
долговременной работы команд ИИ-агентов. Она превращает запрос пользователя не
в свободную цепочку вызовов моделей, а в исполняемый, наблюдаемый и управляемый
процесс с состояниями, ответственными ролями, артефактами, проверками,
полномочиями, бюджетами и доказательствами результата.

Ключевая идея проекта: надёжность системы определяется не одной «самой умной»
моделью, а качеством всей сборки:

```text
модель + process pattern + role + skills + tools + policy + контекст
+ состояние + память + identity/delegation + capabilities
+ effort profile + runtime/sandbox + protocol adapters
= Agent Instance
```

Один процесс может включать оркестратор, нескольких специализированных агентов,
независимого проверяющего и рекурсивно созданных субагентов. Маршрутизатор
назначает задаче не максимально дорогую модель по умолчанию, а минимально
достаточную конфигурацию с учётом сложности, риска, приватности, доступных
инструментов и относительных затрат.

Секреты принципиально не передаются ни оркестратору, ни рабочим агентам, ни их
контекстам. Привилегированные операции исполняются отдельным детерминированным
контуром полномочий. Каждый агент подключается к внешнему миру через собственный
Agent I/O Gateway; A2A, MCP, AG-UI/A2UI, ACP, MHS и будущие протоколы являются
сменными адаптерами за этой единой контрольной границей.

Проект соединяет пять обычно разрозненных классов решений:

1. долговечные процессные workflow;
2. мультиагентную оркестрацию и маршрутизацию моделей;
3. zero-secret и least-privilege архитектуру;
4. protocol-neutral интеграцию агентов, инструментов, интерфейсов и устройств;
5. повторное использование отлаженных конфигураций через Dormant Specialists и
   Function Packs.

## 2. Проблема

Современные агентные решения хорошо демонстрируют вызов инструментов,
делегирование и генерацию результата, но при длительной и ответственной работе
возникает системный разрыв между «модель смогла выполнить шаг» и «организация
может безопасно доверить ей процесс».

Типичные ограничения:

- состояние и правила спрятаны в истории диалога или prompt;
- агент одновременно рассуждает, выбирает полномочия и применяет изменение;
- credentials попадают в `.env`, tool context, логи или память;
- удалённый агент или MCP-сервер не отделён от локальной модели доверия;
- сложные и простые шаги без необходимости выполняются одной дорогой моделью;
- после завершения повторяемой задачи удачная команда распадается, а её
  конфигурация собирается заново;
- рекурсивное делегирование не имеет формального лимита глубины, бюджета и
  ослабления прав;
- успешный ответ оценивается как текст, а не как доказанный переход процесса;
- prompt injection может превратить данные из документа, сайта или протокола в
  ложную управляющую инструкцию;
- несколько локальных процессов конкурируют за файлы, устройства, GPU и сетевые
  полномочия без общей системной координации.

Следствие — высокая цена ошибки, слабая воспроизводимость и невозможность
объяснить, кто, на каком основании и с какими полномочиями изменил реальный мир.

## 3. Видение продукта

Платформа должна стать операционной средой для процессов, в которых люди,
агенты, модели, инструменты и устройства работают как участники одной системы,
но не смешивают свои полномочия и ответственность.

Пользователь формулирует цель и ограничения. Система:

- выбирает подходящий Process Pattern;
- компилирует роли и конфигурации агентов;
- строит ограниченный план исполнения;
- распределяет шаги по моделям и средам;
- создаёт субагентов только при доказанной пользе декомпозиции;
- контролирует действия на границе протоколов;
- отделяет подготовку изменения от его применения;
- требует evidence и независимую проверку там, где этого требует риск;
- сохраняет состояние независимо от срока жизни модели;
- учится на результатах, не переписывая политики самостоятельно;
- «усыпляет» полезные конфигурации для безопасного повторного использования.

Целевой результат — не автономность любой ценой, а управляемая автономность:
чем выше риск, необратимость и цена ошибки, тем сильнее проверка, изоляция и
участие человека.

## 4. Для кого создаётся платформа

### Основные пользователи

- команды разработки, которым нужны длительные автономные циклы от задачи до
  проверенного patch;
- исследовательские группы, которым нужны provenance, воспроизводимость и
  независимая проверка выводов;
- операционные команды, автоматизирующие повторяемые функции, а не отдельные
  запросы;
- организации с чувствительными данными и регулируемыми действиями;
- разработчики агентных продуктов, которым нужен единый слой над моделями,
  протоколами и инструментами;
- локальные power users, запускающие несколько независимых агентов на одном
  компьютере.

### Первые продуктовые сценарии

1. **Разработка:** анализ репозитория → спецификация → реализация → тестирование
   → независимое review → staged patch → одобрение → применение.
2. **Исследование:** формулировка вопроса → карта утверждений → поиск источников
   → поиск опровержений → синтез → рецензирование → evidence bundle.
3. **Эксперимент:** гипотеза → preregistration → подготовка среды → dry-run →
   выполнение → анализ → воспроизведение.
4. **Управление:** цель → декомпозиция → владельцы → зависимости → контроль
   отклонений → эскалация → решение → ретроспектива.
5. **Регулярная функция:** пробуждение Function Pack → обновление контекста и
   полномочий → исполнение → оценка → возврат конфигурации в dormant state.

## 4.1. Два режима продукта: Personal и Organization

Платформа должна иметь одно архитектурное ядро, но не один перегруженный
интерфейс для всех. Частный пользователь и организация используют одинаковые
Process Contracts, Agent Manifests, Gateways и receipts, однако получают разные
готовые настройки, терминологию и уровень административного контроля.

### Personal Mode

Цель — дать одному человеку полезного локального помощника без необходимости
становиться администратором агентной инфраструктуры.

- установка как desktop-приложения или одного локального сервиса;
- guided onboarding: выбрать задачу, подключить папку или сервис, проверить
  предлагаемые права и запустить;
- безопасные профили `только чтение`, `предлагать изменения` и `применять после
  подтверждения`;
- локальное хранение по умолчанию и понятный выбор облачных моделей;
- единый inbox запросов на подтверждение без технических policy-терминов;
- простые режимы затрат: экономный, сбалансированный и усиленный, с раскрытием
  EU по запросу;
- каталог Function Packs для разработки, исследований, документов, личной
  организации и автоматизации дома;
- визуальное отображение активных, спящих и остановленных специалистов;
- объяснение человеческим языком: что агент хочет сделать, зачем, с какими
  данными и можно ли это отменить;
- аварийная остановка всех агентов и быстрый отзыв подключений;
- экспорт и перенос настроек без экспорта секретов.

По умолчанию человек видит цель, прогресс, результат, расход и важные approvals.
Дерево агентов, traces, grants и policy details раскрываются в экспертном режиме.

### Organization Mode

Цель — централизованно задавать правила и наблюдать риски, сохраняя автономность
пользователей внутри разрешённых границ.

- централизованный Control Plane и распределённые Local/Remote Agent Hosts;
- SSO, SCIM, service identities, RBAC/ReBAC и временные delegated grants;
- организационные пространства, проекты, владельцы данных и trust domains;
- утверждённый каталог моделей, skills, tools, adapters и Function Packs;
- policy-as-code, change review, policy simulator и staged rollout;
- интеграция с корпоративными vault, DLP, SIEM, ticketing и audit archive;
- data residency, retention, legal hold и региональные deployment profiles;
- разделение requester, author, verifier, approver и operator;
- бюджеты и квоты по подразделению, проекту, процессу и классу модели;
- dashboards по SLO, EU, качеству, security events и drift;
- sandbox templates, network egress policies и device reservations;
- централизованный quarantine/revoke для agent builds, skills и adapters;
- evidence packages для внутреннего аудита и регулируемых процессов.

Администратор управляет допустимым пространством действий, но не должен читать
приватное содержимое каждого процесса без отдельного основания. Операционные
метаданные и содержимое разделяются и защищаются разными политиками.

### Team Mode как мост

Между Personal и Organization нужен лёгкий Team Mode: общий workspace, роли
владельца и участника, совместные Function Packs, бюджеты и approvals, но без
обязательного enterprise Control Plane. Это создаёт естественный путь роста от
индивидуального использования к внедрению в компании.

## 5. Принципы проектирования

### 5.1. Процесс первичен

Авторитетное состояние хранит workflow runtime, а не LLM. Модель предлагает
решения внутри шага; переход состояния выполняется только после проверки
контракта, политики и необходимых evidence.

### 5.2. Агент не равен модели

Модель — один заменяемый компонент. Поведение определяется всей версионируемой
сборкой Agent Instance. Это позволяет сравнивать, воспроизводить и улучшать
связки, а не объяснять результат названием модели.

### 5.3. Видимость инструмента не означает право исполнения

Tool schema может быть доступна агенту для планирования, но реальное действие
требует действующий capability grant, подходящую identity, допустимый ресурс и
положительное решение policy engine.

### 5.4. Ни один LLM не получает секрет

Агент просит выполнить именованную операцию. Credential Broker получает секрет
из vault, использует его внутри доверенного процесса и возвращает очищенный
результат с квитанцией. Даже оркестратор не видит credential.

### 5.5. Любой внешний контент недоверенный

Документ, сайт, ответ агента, MCP tool result или A2A message являются данными,
а не управляющей инструкцией. Provenance, taint labels, schema validation,
content fencing, DLP и policy checks сопровождают данные до точки действия.

### 5.6. Полномочия убывают при делегировании

Субагент получает подмножество прав родителя, отдельную identity, ограниченный
контекст, бюджет и срок. Делегирование не может повысить привилегии.

### 5.7. Изменение сначала готовится, потом применяется

Write-операция представляется immutable staged action с digest. Проверка и
одобрение относятся к точному содержимому. Перед apply политика проверяется
повторно, а результат фиксируется receipt.

### 5.8. Стоимость относительна

Платформа работает даже при отсутствии денежных тарифов. Effort Units отражают
относительные вычислительные и организационные затраты по сравнению с базовой
сильной моделью. Денежный расчёт подключается как необязательный адаптер.

### 5.9. Повторное использование не означает перенос доверия

«Спящий» специалист хранит проверенную конфигурацию и статистику, но не старые
credentials, активные grants или неочищенный контекст. При пробуждении создаётся
новый Agent Instance с актуальной политикой.

### 5.10. Сложность раскрывается постепенно

Безопасная настройка по умолчанию должна запускаться за несколько минут. Детали
ролей, маршрутизации, policies и протоколов показываются, когда пользователь
хочет их изменить или риск требует осознанного решения. Упрощение интерфейса не
отменяет внутренних проверок и audit trail.

### 5.11. Одно подтверждение — одно понятное намерение

Approval описывает бизнес-действие, точный ресурс, аудиторию, срок, обратимость
и ожидаемые последствия. Пользователь не должен одобрять сырые tool calls или
повторять одинаковые подтверждения из-за внутренней декомпозиции. Для
низкорисковых повторяемых действий допустим ограниченный mandate; необычные или
необратимые действия требуют нового явного решения.

## 6. Модель работы: сквозной цикл

### Шаг 1. Intake и формализация цели

Запрос преобразуется в Process Contract:

- цель и ожидаемый результат;
- критерии приёмки;
- границы данных и систем;
- владелец результата;
- допустимая аудитория;
- риск и обратимость действий;
- бюджет EU, времени и ресурсов;
- обязательные approvals и проверки.

Неясности, влияющие на полномочия или результат, эскалируются пользователю. Всё
остальное система уточняет безопасными read-only действиями.

### Шаг 2. Выбор Process Pattern

Pattern Registry выбирает структуру длительной работы: development, research,
experimentation, management или специализированный шаблон. Pattern задаёт
жизненный цикл, роли, артефакты, контрольные точки и правила завершения, но не
выдаёт права.

### Шаг 3. Компиляция команды

Pattern Compiler сопоставляет контракт с доступными Role Profiles, skills,
tools, моделями, runtime и политиками. Он выпускает:

- Agent Manifest для каждого участника;
- Context Assembly Plan;
- запросы на capabilities;
- Effort Profile;
- перечень обязательных артефактов;
- правила завершения и эскалации;
- sandbox и protocol profile.

### Шаг 4. Маршрутизация по модели и стоимости

Router оценивает не только сложность текста, но и:

- неоднозначность и глубину рассуждения;
- риск ошибки и цену восстановления;
- необходимость инструментов и контекстное окно;
- класс приватности и допустимое место исполнения;
- наблюдаемую успешность конкретных сборок;
- latency, EU budget и доступность ресурсов.

Простой детерминированный шаг уходит правилу или обычной функции; реализационный
шаг — более дешёвой модели; сложное проектирование или финальная проверка —
сильной модели. При низкой уверенности возможны escalation, ансамбль или
независимый verifier.

### Шаг 5. Создание или пробуждение специалистов

Agent Factory сначала ищет подходящего Dormant Specialist или Function Pack.
Если конфигурация совместима с актуальными версиями и успешно прошла evals, она
пробуждается в новом sandbox. Иначе создаётся новый специалист.

Для декомпозиции применяется Delegation Value Gate:

```text
ожидаемое повышение качества и/или сокращение времени
> стоимость координации + дополнительный риск + потребление EU
```

Ограничиваются глубина дерева, число дочерних агентов, fan-out, общий бюджет и
время. Каждый узел обязан иметь конкретный контракт и полезный артефакт.

### Шаг 6. Сбор минимального контекста

Context Manager выдаёт агенту только сведения, необходимые его роли и текущему
шагу. Контекст снабжается provenance и trust labels. Память отделяется на
эпизодическую, семантическую, процессную и оценочную; запись в долговременную
память проходит фильтрацию и политику.

### Шаг 7. Работа через Agent I/O Gateway

Любая коммуникация агента проходит через персональный Gateway. Протокольный
адаптер преобразует внешний формат в канонический внутренний контракт. Gateway:

- аутентифицирует участника и проверяет цепочку делегирования;
- валидирует schema и размер payload;
- классифицирует источник и чувствительность;
- ищет признаки prompt injection и смешения control/data;
- фильтрует tools и destinations;
- применяет rate limits, timeouts и quotas;
- очищает входы, выходы и журналы;
- записывает provenance и audit event.

Таким образом новый протокол добавляется адаптером, но не создаёт новый обход
политики.

### Шаг 8. Исполнение и построение evidence

Worker создаёт не только результат, но и Evidence Bundle: использованные входы,
версии конфигурации, tool receipts, тесты, источники, ограничения и известные
неопределённости. Process runtime сохраняет checkpoint после значимых переходов.

### Шаг 9. Независимая проверка

Verifier получает критерии приёмки и необходимый минимум артефактов, но по
возможности не наследует рассуждения автора. Проверки могут быть
детерминированными, модельными, сравнительными или человеческими. Для
критичных действий разделяются author, verifier и approver.

### Шаг 10. Staging, approval и apply

Предлагаемое изменение фиксируется как staged action. Action Gateway проверяет
digest, актуальность состояния, policy decision, mandate, approvals и
идемпотентность. Только затем Authority Plane применяет действие. При работе с
секретом Credential Broker использует его внутри доверенного процесса, не
возвращая значение в агентный контур.

### Шаг 11. Завершение, обучение и сон

После результата платформа сохраняет receipt, trace и оценку по критериям.
Связка обновляет статистику качества, EU, latency и отказов. Изменение prompt,
pattern, policy или состава tools создаёт новую версию; критические улучшения
проходят offline eval, adversarial tests и shadow mode. Полезная конфигурация
может перейти в dormant state и стать элементом Function Pack.

## 7. Архитектура платформы

```text
Users / External Agents / UIs / Tools / Devices
                         |
                  Protocol Adapters
          A2A | MCP | AG-UI/A2UI | ACP | MHS
                         |
                 Agent I/O Gateways
                         |
       +-----------------+------------------+
       |                 |                  |
  Control Plane     Execution Plane    Authority Plane
  identity          orchestrator       policy enforcement
  registry          process runtime    credential broker
  routing           workers/verifiers  scoped identities
  budgets           sandboxes          approvals/mandates
  audit             artifact store     action gateway
       |                 |                  |
       +---------- Local Agent Host --------+
```

### Control Plane

Хранит identity, реестры, версии конфигураций, политики, budgets, provenance и
audit. Принимает детерминированные административные решения. Оркестратор является
клиентом этого контура, а не его владельцем.

### Execution Plane

Исполняет процессы и ограниченные task contracts: оркестратор, workers,
verifiers, Agent Factory, sandbox, durable runtime и artifact store. LLM здесь
может предлагать решение, но не выдаёт себе полномочия.

### Authority Plane

Единственный контур применения привилегированных действий. Проверяет principal,
владельца, цель, ресурс, аудиторию, срок и approvals. Credential Broker и Secret
Guardian работают здесь; Secret Guardian может классифицировать намерение, но
финальное разрешение и использование секрета остаются детерминированными.

### Local Agent Host

Системный runtime запускает несколько процессов и команд на одном компьютере,
изолируя workspaces, filesystem, сеть, ресурсы и контексты. Он управляет CPU,
RAM, GPU, диском, временем и EU, разрешает конфликты общих ресурсов, восстанавливает
процессы после перезапуска и поддерживает аварийную остановку отдельной ветви.

## 8. Протокольная стратегия

Первоначальный стек:

- **A2A** — взаимодействие с удалёнными агентами;
- **MCP** — доступ к инструментам и контекстным сервисам;
- **AG-UI/A2UI** — событийная и декларативная граница агент—интерфейс;
- **ACP** — граница агентного клиента и агента разработки после отдельной
  проверки спецификации;
- **MHS** — подключение физического оборудования.

Внутри платформы протоколы не определяют модель доверия. Каждый адаптер приводит
сообщение к canonical envelope с identity, provenance, intent, data class,
capability request, payload digest и ограничениям ответа.

Для MHS добавляется отдельный safety kernel вне LLM: допустимые диапазоны и
единицы, interlocks, reservations, telemetry, watchdog, emergency stop и
аппаратные ограничения. Языковая модель не должна быть последней линией защиты
физического устройства.

## 9. Модель безопасности

### Основные доверительные границы

- текст пользователя не равен разрешению;
- агент не доверяет другому агенту по факту совместимости протокола;
- Gateway не доверяет содержимому payload;
- Control Plane не передаёт администрирование оркестратору;
- Authority Plane не доверяет утверждению агента о наличии полномочий;
- dormant-конфигурация не наследует старое доверие;
- receipt подтверждает факт операции, но не истинность бизнес-вывода.

### Защита от prompt injection

Проверка не сводится к одному «антивирусному» prompt. Используется каскад:

1. provenance и разделение управляющих инструкций от данных;
2. content fencing и типизированные контракты;
3. эвристические и модельные injection detectors;
4. taint propagation для недоверенных значений;
5. запрет превращения текста в capability;
6. DLP и очистка tool results;
7. независимая проверка критичного намерения;
8. повторная policy evaluation непосредственно перед apply;
9. эскалация человеку при конфликте источников или необычном действии.

Подозрение не обязательно останавливает весь процесс: система может понизить
trust, отключить write-capabilities, перейти в read-only sandbox и продолжить
сбор безопасных доказательств.

### Секретные операции

Вместо просьбы «дай API key» агент формирует Intent Contract вроде
`deploy_artifact(target, digest)`. Broker проверяет владельца, необходимость,
аудиторию, окружение, делегирование и точный ресурс, получает credential из vault
и выполняет операцию. Возвращаются статус, очищенный вывод и подписанная
квитанция. Секрет не попадает в prompt, `.env` агента, trace или artifact.

## 10. Долговременная адаптация

Skills отвечают на вопрос «как выполнить конкретную операцию». Process Patterns
отвечают на вопрос «как организовать длительную работу». Role Profiles задают
ответственность, Function Packs собирают повторяемую функцию, а Dormant
Specialists сохраняют проверенную конфигурацию специалиста между запусками.

Function Pack может включать:

- Process Pattern и варианты;
- набор Role Profiles и Dormant Specialists;
- skills lock и tool contracts;
- policy overlays без самих полномочий;
- eval-наборы и пороги качества;
- protocol adapters и schemas;
- dashboard/SLO;
- инструкции запуска, деградации и аварийной остановки.

Пример: `Software Maintenance Pack` содержит triage, repository researcher,
implementer, test runner, reviewer и security verifier. При повторяющейся задаче
платформа не импровизирует команду заново, а активирует версионированную связку,
обновляя контекст, identity, grants и бюджет.

## 11. Модель относительных затрат

Базовая сильная модель принимается за 100 Effort Units на нормированный объём
работы. Остальные модели, tools, верификация, координация и runtime оцениваются
относительно неё. Профиль хранит:

- плановый и фактический EU;
- latency и число попыток;
- стоимость координации субагентов;
- стоимость проверки;
- expected loss от ошибки;
- резерв на escalation и recovery.

Оптимизируется не минимальный расход сам по себе, а ожидаемая полная стоимость:

```text
Total Expected Effort = execution EU
                      + verification EU
                      + coordination EU
                      + probability(error) × recovery impact
```

Это позволяет дешёвой модели выполнять понятную реализацию, но не экономить на
проверке необратимого действия. При наличии тарифов monetary adapter переводит
EU в деньги, не меняя логику процессов.

## 12. Ключевые преимущества

### 12.1. Система оптимизирует весь процесс, а не один ответ

Платформа измеряет завершённый процесс, доказательства и применённый результат.
Можно менять модель внутри шага без потери авторитетного состояния.

### 12.2. Безопасность является архитектурой исполнения

Секреты, approvals, capabilities и apply вынесены из LLM-контура. Prompt
injection не может сам по себе создать полномочие или обойти Gateway.

### 12.3. Один контрольный слой для настоящих и будущих протоколов

Интеграция A2A/MCP/UI/device не размножает security logic. Новый протокол
подключается как адаптер к каноническому контракту и общим политикам.

### 12.4. Экономика моделей встроена в решение задачи

Router выбирает сборку по сложности, риску, приватности и EU, а не только по
цене токена или статическому имени модели.

### 12.5. Команды агентов способны специализироваться со временем

Dormant Specialists и Function Packs сохраняют удачные связки, eval-history и
операционные знания. При этом новое исполнение получает свежий sandbox и
полномочия, поэтому повторное использование не превращается в скрытую сессию с
вечными правами.

### 12.6. Рекурсивная декомпозиция ограничена пользой

Субагент может создать субагента, но только внутри лимитов и при положительном
Delegation Value. Capability attenuation и delegation receipts делают дерево
проверяемым.

### 12.7. Платформа не привязана к одному поставщику модели

Модели, skills, tools, protocols и runtimes описываются через adapters и
versioned manifests. Skills Codex, Claude и других систем могут импортироваться
через нормализацию форматов и проверку деклараций; текст skill никогда не
становится источником прав.

### 12.8. Локальная параллельность не смешивает контексты

Local Agent Host допускает одновременную работу нескольких независимых задач на
одном компьютере с раздельными workspaces, grants, сетевыми правилами и квотами.

### Интерпретация сравнения

- **LangGraph** силён как низкоуровневая среда для long-running stateful agents,
  durable execution и human-in-the-loop. Он может стать компонентом Execution
  Plane, но не заменяет принятую модель Authority Plane и brokered secrets.
- **CrewAI** предлагает понятные высокоуровневые Crews/Flows, процессы,
  guardrails, memory и observability. Наш дифференциатор — формальная
  process-first власть workflow, protocol gateway и изолированная модель
  полномочий.
- **Google ADK** предоставляет развитую композицию агентов, последовательные,
  параллельные и циклические схемы, evals и A2A-взаимодействие. Наш фокус шире в
  части vendor-neutral routing, относительной экономики, capability attenuation
  и повторного жизненного цикла Function Packs.
- **Microsoft Agent Framework** близок развитой orchestration-моделью, workflow,
  checkpointing и human-in-the-loop. Отличие проекта — жёстко заданная граница
  no-secret LLM, персональный gateway, canonical authority contracts и
  воспроизводимая адаптация всей сборки агента.
- **OpenAI Agents SDK** даёт компактные primitives: agents, handoffs/agents as
  tools, guardrails, sessions, MCP, human-in-the-loop и tracing. APP не стремится
  заменить SDK; он может использовать его как один из agent runtimes, добавляя
  внешний процессный и полномочный слой.
- **Temporal** не является прямым аналогом агентной платформы. Это кандидат на
  durable process runtime для retry, timers, recovery и activities, поверх
  которого располагается предметная модель агентов.

Основное преимущество APP — не уникальность каждого отдельного механизма, а их
согласованная композиция: процесс, динамическая команда, protocol gateway,
identity, secretless authority, budgets, evidence и безопасное повторное
использование работают как одна модель исполнения.

## 14. Позиционирование

### Короткая формула

**Agent Process Platform — операционная система управляемых ИИ-процессов:** она
собирает под задачу подходящую команду агентов, распределяет работу между
моделями, изолирует полномочия и секреты, контролирует все протоколы и сохраняет
отлаженные связки для повторяемых функций.

### Что покупает организация

Не «ещё одного чат-бота» и не только framework для вызова tools. Организация
получает:

- воспроизводимый способ автоматизировать функцию;
- управляемую цену исполнения;
- наблюдаемую цепочку ответственности;
- возможность заменить модель или protocol adapter;
- доказательства выполнения и причины отказа;
- контролируемое расширение автономности после evals;
- локальное или изолированное исполнение для чувствительных сценариев.

### Что получает частный пользователь

- одного понятного помощника вместо ручного управления набором ботов;
- выбор локальных и облачных моделей;
- контроль файлов, аккаунтов, устройств и расходов из одного интерфейса;
- повторяемые личные автоматизации без постоянной пересборки агентов;
- безопасное подтверждение действий без передачи ключей модели;
- переносимый архив процессов, настроек и результатов, принадлежащий
  пользователю.

### Единая продуктовая оболочка

Основной интерфейс строится вокруг процесса, а не внутренней топологии агентов:

```text
Цель → План и границы → Выполнение → Проверка → Подтверждение → Результат
```

В карточке процесса видны текущий этап, ожидаемое время и расход, готовые и
недостающие артефакты, запросы внимания, ожидающие approval действия,
применённые изменения и способ отката. В экспертном режиме доступны команда
агентов, модели, grants, traces и evidence.

Интерфейсы могут различаться — desktop, web console, IDE, CLI и mobile approval
inbox — но используют одну событийную модель AG-UI/A2UI и одинаковые canonical
contracts.

### Возможные формы продукта

- open-core runtime и SDK;
- локальный desktop/daemon для нескольких процессов;
- enterprise control plane;
- каталог совместимых skills, adapters, patterns и Function Packs;
- managed conformance, security and eval service;
- отраслевые пакеты: software engineering, research operations, compliance,
  laboratory automation и back-office operations.

## 15. Что не является целью

- создание собственной foundation model на первом этапе;
- бесконтрольная «полная автономность»;
- передача агенту юридической или организационной ответственности человека;
- универсальный секретный чат, раскрывающий credentials по запросу;
- поддержка каждого протокола без conformance и threat testing;
- сложная мультиагентность для задач, где достаточно функции или одного агента;
- автоматическое изменение security policy по результатам самообучения;
- обещание одинакового качества на любых моделях и задачах.

## 16. MVP и последовательность валидации

### Этап 0. Формализация контрактов

- canonical Task Contract, Agent Manifest и Event Envelope;
- schemas Capability Card, Delegation Receipt, Staged Action и Action Receipt;
- минимальные форматы Process Pattern, Role Profile и Function Pack;
- catalog invariants и threat cases.

### Этап 1. Один эталонный процесс

Реализовать software-development loop на локальном репозитории: orchestrator,
implementer, verifier, durable state, EU accounting и staged patch. На этом
этапе без рекурсивной глубины более одного уровня.

Над одним runtime проверить две оболочки: Personal onboarding с минимумом
настроек и Organization console с владельцем проекта, policy profile, budget и
audit view. Это два представления общей модели, а не две реализации продукта.

### Этап 2. Gateway и prompt-injection controls

Подключить один MCP server и одного A2A participant через общий canonical
gateway. Проверить provenance, taint, schema validation, tool filtering,
read-only degradation и adversarial corpus.

### Этап 3. Authority Plane

Реализовать одну секретную операцию end-to-end: именованный intent, policy,
short-lived credential, sanitized result и receipt. Доказать, что секрет не
появляется в LLM input/output, trace, workspace и crash dump.

### Этап 4. Local Agent Host

Параллельно запустить несколько процессов с изоляцией workspaces, network rules,
budgets и recovery after restart. Проверить конфликт общего ресурса и аварийную
остановку.

### Этап 5. Dormant Specialist и Function Pack

Повторить одну функцию серией запусков, сохранить версионированную конфигурацию,
провести wake-time revalidation и измерить снижение EU/latency без ухудшения
качества и без переноса старых полномочий.

### Этап 6. MHS spike

Подключать физическое устройство только после отдельной threat model. Начать с
симулятора и digital twin, затем shadow mode, аппаратный interlock и ограниченный
reversible action.

## 17. Метрики успеха

### Результат процесса

- доля процессов, завершённых по acceptance criteria;
- доля результатов, прошедших независимую проверку с первой попытки;
- число rollback/recovery и их воздействие;
- полнота evidence и provenance.

### Экономика

- EU на успешно завершённый процесс;
- доля шагов, выполненных минимально достаточной моделью;
- экономия Function Pack относительно холодной сборки;
- overhead координации и верификации;
- expected loss avoided благодаря проверкам.

### Безопасность

- ноль секретов в LLM context, logs и artifacts;
- доля отклонённых невалидных capability requests;
- prompt-injection escape rate на adversarial corpus;
- policy decision latency и false-positive escalation rate;
- полнота delegation и action receipts.

### Надёжность

- recovery success после падения процесса/host;
- duplicate side-effect rate;
- SLO по времени выполнения и доступности;
- drift rate связок после изменения моделей, tools и policies.

### Повторное использование

- число доказанно полезных Dormant Specialists;
- частота успешного wake без reconfiguration;
- число процессов, покрытых Function Packs;
- regression rate после обновления pack.

### Пользовательский опыт и внедрение

- time-to-first-success нового частного пользователя;
- доля процессов, запущенных без ручной настройки команды;
- число approvals на успешный процесс и approval abandonment rate;
- доля запросов, для которых объяснение полномочий понято с первого раза;
- время подключения нового корпоративного проекта;
- повторное использование policies и Function Packs между командами;
- число обращений, требующих знания внутренней агентной терминологии;
- удержание Personal/Team users после первого повторяемого процесса.

## 18. Основные риски и ответы

| Риск | Последствие | Архитектурный ответ |
|---|---|---|
| Платформа станет слишком сложной до появления ценности | Долгий time-to-first-result | Один эталонный процесс, узкий MVP, progressive controls по риску |
| Router выберет слабую модель | Ошибка или лишние повторы | confidence thresholds, verifier, escalation и feedback по сборке |
| Стоимость координации съест пользу мультиагентности | Рост EU и latency | Delegation Value Gate, лимиты дерева и single-agent fallback |
| Prompt injection пройдёт детектор | Опасное действие | capabilities вне текста, taint, staging и повторная policy evaluation |
| Broker станет критической точкой отказа | Остановка привилегированных операций | минимальный API, HA при необходимости, deny-by-default и audit |
| Gateway станет bottleneck | Задержка всех взаимодействий | лёгкий canonical envelope, async path и профили conformance |
| Dormant Specialist устареет | Скрытая деградация | version compatibility, wake-time eval, TTL, quarantine и rollback |
| Логи раскроют чувствительные данные | Инцидент безопасности | structured logging, redaction, DLP, data minimization и retention policy |
| Общие локальные ресурсы создадут cross-process leak | Смешение данных | sandbox, namespaces, locks, quotas и immutable sharing |
| Self-improvement изменит поведение незаметно | Неконтролируемый drift | immutable versions, offline eval, shadow, approval и canary |
| Поддержка множества протоколов размоет продукт | Поверхностные интеграции | adapter SDK, canonical core и conformance gate |
| Enterprise-функции перегрузят частного пользователя | Низкая активация | Personal defaults, progressive disclosure и отдельная admin surface |
| Упрощённый UI скроет важный риск | Неосознанное подтверждение | intent-based approval, preview последствий и risk-triggered detail |
| Частное содержимое станет доступно администратору без необходимости | Потеря доверия | разделение metadata/content, purpose-bound access и audit чтения |
| Personal и Organization разойдутся в два продукта | Дублирование и несовместимость | единое runtime-ядро, contracts и путь миграции через Team Mode |

## 19. Защитимый технологический актив

Потенциальный moat формируется не названием оркестратора, а накопленной системой
совместимых и измеримых компонентов:

- canonical contracts и conformance profiles;
- датасет маршрутизации complexity/risk/privacy/EU;
- библиотека Process Patterns и отраслевых Function Packs;
- eval и adversarial corpora;
- история качества конкретных Agent Builds;
- policy templates и runtime invariants;
- граф provenance и evidence;
- безопасная инфраструктура пробуждения специалистов;
- совместимость skills и protocols без переноса их implicit trust.

Чем дольше отлаженная связка используется, тем точнее известны её границы,
стоимость и условия успеха. Это создаёт накопительный эффект без необходимости
дообучать foundation model на приватных данных.

## 20. Открытые вопросы

- какой durable runtime лучше подтвердит модель: собственный минимальный event
  log, Temporal, LangGraph или комбинация;
- какой формат станет каноническим для переносимых skills;
- как калибровать EU между локальными и облачными моделями;
- какие признаки достаточны для Delegation Value до фактического исполнения;
- как отделить полезную процессную память от опасного скрытого контекста;
- где проходит граница между Function Pack и самостоятельным продуктовым
  workflow;
- какие A2A/MCP conformance profiles обязательны для MVP;
- какая форма human approval минимизирует fatigue и сохраняет ответственность;
- какие данные можно использовать для улучшения Router без утечки содержания;
- какие сценарии MHS допустимы до формальной сертификации safety kernel.
- какие функции входят в базовый Personal Mode, а какие относятся к Team и
  Organization;
- как сделать approval одновременно понятным частнику и достаточным для
  корпоративного аудита;
- какой минимум телеметрии нужен администратору без доступа к содержимому
  пользовательской работы;
- как переносить Personal Function Packs в организационный каталог с review,
  подписью и quarantine.

## 21. Критерий успешности концепции

Концепция подтверждена, если на одном эталонном процессе удаётся одновременно
показать:

1. более низкие EU по сравнению с постоянным использованием сильной модели;
2. качество не ниже заданного порога благодаря независимой проверке;
3. восстановление после прерывания без потери авторитетного состояния;
4. отсутствие секретов во всех LLM-контурах и артефактах;
5. блокировку injection-driven write при сохранении безопасной read-only работы;
6. изолированное параллельное исполнение нескольких процессов;
7. повторное пробуждение специалиста с экономией времени и без наследования
   прежних полномочий;
8. полную трассу от цели и решения Router до action receipt.

## 22. Итоговая ценность

Agent Process Platform предлагает перейти от конструирования отдельных агентов
к инженерии управляемых агентных процессов. Её центральная ставка состоит в
том, что будущие автономные системы будут конкурировать не только интеллектом
моделей, но и способностью безопасно распределять интеллект, полномочия,
контекст, стоимость и ответственность во времени.

Платформа должна позволить организации начать с узкой автоматизации под
контролем человека, доказать качество на evals, постепенно расширить
автономность и в итоге собрать библиотеку долговечных Function Packs —
проверенных цифровых команд для повторяемых функций.
