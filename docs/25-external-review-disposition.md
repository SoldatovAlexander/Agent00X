# Разбор внешней оценки проектного брифа

Статус: рассмотрено  
Дата: 2026-09-04

## Назначение

Документ отделяет полезные замечания внешней оценки от принятых архитектурных
решений. Положительная рецензия не является доказательством реализуемости;
критическое замечание не становится требованием без анализа и эксперимента.

## Реестр замечаний

| Замечание | Позиция проекта | Решение | Проверка |
|---|---|---|---|
| Local Agent Host потребует собственного гипервизора | Оценка чрезмерна | Использовать готовые sandbox backends за единым интерфейсом | VP-12 и sandbox spike |
| Полный security cascade создаст критический latency | Риск реален, но не каждый payload требует одинаковых проверок | Fast/Slow/Degraded Path по риску | VP-05 и новые latency metrics |
| Минимальный контекст может ухудшить качество | Риск реален | Измерять sufficiency, разрешить контролируемое расширение контекста | VP-08 и отдельный context experiment |
| Process Contract создаёт UX friction | Риск реален для Personal Mode | Выводить контракт из естественного запроса и подтверждать только существенные границы | UX validation |
| Approval fatigue снизит автономность | Риск реален | Intent-level approvals и ограниченные mandates | VP-06 и UX validation |
| Broker можно проверить отдельно | Не согласовано | Broker неделим с Gateway, policy и typed actuator | Thin Slice M2/M3 |
| MVP должен объединить процесс разработки и secretless action | Принято с уточнением | Агент готовит staged change; доверенный GitHub Actuator публикует PR | `24-mvp-final-plan.md` |
| Агент с read-only репозиторием создаёт commit | Логическое противоречие | Snapshot read-only, ephemeral workspace writable, publish выполняет Actuator | M1/M2 |
| Постоянный GitHub token берётся из Vault | Нежелательный default | GitHub App и short-lived installation token | M2, VP-03 |
| Внутренний A2A можно считать low-risk | Только условно | Fast Path не равен trust; privilege transitions всегда Slow Path | VP-05, VP-10 |
| MHS следует включить в ранний MVP | Не принято | Только contract stub; реальный hardware остаётся отдельным R&D gate | VP-11 после MVP |

## Уточнённые инженерные принципы

1. Не строить инфраструктуру, которую можно надёжно получить готовым backend.
2. Не применять дорогую проверку без сигнала риска, но сохранять дешёвые
   инварианты на каждом переходе.
3. Не смешивать policy decision, credential handling и domain action в одном
   компоненте.
4. Не давать агенту credential ради демонстрации «автономности».
5. Не считать аутентифицированный внутренний канал доверенным по содержанию.
6. Не начинать с горизонтальной платформы; доказать один вертикальный результат.
7. Не переносить ограничения UX на пользователя: система сама предлагает
   контракт, человек подтверждает существенные последствия.

## Изменение приоритета

Ранее validation plan последовательно проверял множество foundation-компонентов.
Теперь те же проверки группируются вокруг одного executable thin slice. Это не
отмена security gates, а изменение порядка сборки: ценность и доверительные
границы становятся наблюдаемы в одном сценарии раньше.

## Не принятые предположения

- необходимость собственного гипервизора;
- доверие ко всему внутреннему A2A-трафику;
- использование OPA как обязательной технологии MVP;
- хранение долгоживущего PAT как базовый сценарий;
- включение MHS, рекурсивных команд и marketplace в первый вертикальный срез.
