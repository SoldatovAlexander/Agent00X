# Модель памяти и сроков хранения

Статус: концепция принята; реализация, политики хранения и миграции не созданы

Версия: 0.1

Дата: 2026-09-09

## 1. Назначение

Память помогает агенту принимать решения, но не должна быть бесконечной,
неструктурированной или автоматически доступной всем участникам. Эта модель
задаёт слои памяти, границы доступа и суммаризацию истории. Она применяется к
памяти процесса, артефактам, событиям наблюдения и проверенным корректировкам;
секреты в неё не входят.

Память не заменяет Process State. Runtime остаётся источником истины о текущем
состоянии, approval и внешнем действии. Наблюдательная история отвечает на
вопрос «что произошло», а память — «какие разрешённые сведения могут помочь
в текущем решении».

## 2. Слои и доступ

| Слой | Содержание | Доступ агента | Изменение |
|---|---|---|---|
| Process State | Состояние, переходы, ожидания, approvals, deadlines | Только снимок по Task Contract | Только Runtime |
| Task Context | Цель, критерии, разрешённые данные и ссылки | Конкретный агент/субагент, минимальный scope | Context Compiler по процессу |
| Artifact Store | Версионированные файлы, evidence, результаты tools, provenance | По классификации, purpose и ссылке | Зарегистрированные writers |
| Procedural Memory | Process Patterns, правила, роли, разрешённые инструкции | Разрешённая версия по роли | Review и versioning |
| Learning Memory | Утверждённые Learning Corrections, примеры, границы применимости | Только релевантные проверенные записи | Отдельный review |
| Working Memory | Временный план и промежуточные выводы запуска | Только агент одного run | Сам агент в sandbox; не источник истины |
| Observation History | Events, checkpoints, результаты и пробелы | Observer/человек или агент с явным read scope | Только Collector, append-only |
| User/Organization Memory | Предпочтения, владельцы, устойчивые настройки | Явный purpose-bound scope | Владелец или уполномоченный сервис |
| Secrets | Пароли, ключи, токены | Никогда не доступны LLM, Observer или субагенту | Только защищённый Broker/secret service |

Субагент не наследует всю память родителя. Он получает только свой Task Context,
ссылки на нужные артефакты, версию процедуры, необходимые проверенные примеры и
ограниченный срок доступа. Старые grants, approvals, рабочие заметки других
агентов и секреты не передаются автоматически.

## 3. Базовая ретенция и суммаризация

Политика относится к данным, которые разрешено хранить. Классификация данных,
договорные обязательства, legal hold, запрос на удаление или правило владельца
могут сделать срок короче, длиннее или запретить суммаризацию. Такие исключения
применяет policy, не LLM.

| Возраст записи | Рабочее представление | Исходные данные | Использование по умолчанию |
|---|---|---|---|
| До 6 месяцев | Полная разрешённая история и артефакты | Доступны в установленном scope | Текущая работа, investigation, обучение |
| От 6 до 12 месяцев | Обязательная месячная сводка | Архивируются либо удаляются согласно classification/retention policy | Агент видит сводку; оригинал открывается только при праве и необходимости |
| Более 12 месяцев | Обязательная годовая тематическая сводка | Не являются частью обычного контекста; архивируются или удаляются по policy | Агент видит годовую сводку и индекс значимых фактов |
| После срока хранения | Нет активной памяти | Удаление или законный архив по policy | Недоступно |

Месячная сводка строится для каждого календарного месяца, годовая — для
календарного года и темы/функции. Более поздняя сводка может использовать более
ранние сводки, но не должна выдавать выводы за первичные факты.

## 4. Доказательный минимум

Суммаризация не переписывает append-only историю и не делает старый факт
недоказуемым. Для критичных действий сохраняется минимальная проверяемая запись
на срок, установленный политикой: `event_id`, process/run/branch ID, время,
тип действия, actor/service identity, digest входа и результата, policy/approval
reference, idempotency key, outcome и ссылка на retention decision.

К критичным относятся approval, policy decision, Credential Broker operation,
Action Receipt, внешний side effect, security incident, отказ в правах,
checkpoint перед внешним действием и Learning Correction. Их исходное содержимое
может быть удалено по правилам данных, но сводка не вправе обещать, что оно ещё
доступно. Digest не восстанавливает удалённый контент.

## 5. Формат сводки

Каждая сводка — отдельный версионированный артефакт, а не замена исходных событий.
Минимальные поля:

| Поле | Назначение |
|---|---|
| `summary_id`, `schema_version`, `summary_kind` | Идентичность и вид: monthly/yearly/topic |
| `period_start`, `period_end`, `scope` | Временной и предметный охват |
| `source_refs`, `source_digest` | Ссылки на доступные исходники и digest полного набора на момент суммаризации |
| `content`, `significant_event_refs` | Сжатое содержание и ссылки на критичные факты |
| `omissions`, `redaction_status`, `completeness` | Что не вошло, что скрыто и насколько вывод полный |
| `summarizer_build_id`, `created_at` | Какая версия механизма построила сводку и когда |
| `retention_until`, `archive_or_deletion_status` | Судьба исходных данных и самой сводки |

LLM может подготовить текст сводки, но deterministic validation проверяет
структуру, scope, ссылки и права. Сводка обязана отделять факты, заявленные
основания решений и интерпретации. Она не может создавать capability, approval,
policy decision или новую Learning Correction.

## 6. Контекст для агента

Context Compiler собирает память в порядке приоритета:

1. Process State и Task Contract текущего запуска.
2. Непосредственно связанные свежие артефакты и evidence.
3. Подходящие утверждённые Learning Corrections.
4. Месячные/годовые сводки по функции или владельцу данных.
5. Исходные архивы — только по явному запросу, purpose, classification и budget.

Каждая переданная единица имеет `memory_ref`, версию/digest, origin,
classification, permitted uses, expiry и причину включения. Агент обязан
различать «сводка говорит» и «исходный артефакт подтверждает». Неполная сводка
не достаточна для необратимого или внешнего действия: требуется актуальная
проверка источника, policy и approval.

## 7. Связь с Observer и обучением

Observer строит исторический отчёт по Observation History, а не только по
сводке. Если исходник удалён или недоступен, он сообщает об этом. Учебная ветка
использует checkpoint и артефакты, доступные по политике; если их уже нет,
воспроизведение ограничено и не подменяется реконструкцией из сводки.

Learning Correction может ссылаться на старый случай через доказательный минимум
и сводку, но применяется лишь после проверки условий применимости на актуальных
данных. Суммаризация не превращает старое решение в вечное правило.

## 8. Проверка и следующие действия

Для V-20/VP-23 нужно реализовать и проверить:

- автоматическое создание месячных и годовых сводок по policy;
- сохранение source digest, critical references, redaction и полноты;
- отсутствие доступа субагента к памяти вне scope;
- отсутствие секретов в сводках и prompt injection через их текст;
- корректную реакцию на удалённый исходник, legal hold и retention exception;
- невозможность применить сводку вместо актуального approval или источника;
- ограниченный контекст агента: актуальные данные приоритетнее старого резюме.

До реализации это решение является требованием к R0/R3, а не работающей
retention system.
